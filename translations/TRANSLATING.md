# Translating Caruspex

Caruspex speaks German and English in the code itself. Every other language
lives in `translations/<code>/` as JSON files and is built into the program
from there.

## Where texts come from

**Core texts** (fault codes with causes and checks, value names, protocol
messages, report texts) are written in the Rust crates and in
`app/src-tauri` as `l("de", "en")` or `Text::new("de", "en")`. The German
text is the source, the English one is the key the other languages are looked
up by.

- `py -I tools/i18n_rust.py` lists the texts that have no entry in
  `translations/source/core_*.json` yet.
- `py -I tools/i18n_rust.py --write` appends them with new ids to
  `translations/source/core_x2.json`. Each entry has `id`, `de` and `en`.
- Translators fill `translations/<code>/core_x2.json` (and the other
  `core_*.json` files for older ids) as one JSON object from id to text.
- `py -I tools/i18n_rust.py --strict` is the CI check: it fails when a text
  has no source entry or when some language lacks a translation for an id.
- The crate `caruspex-i18n` reads `translations/source/core_*.json` and
  `translations/<code>/core_*.json` at build time (`build.rs`) and joins them
  into one catalog per language. Nothing needs to be generated by hand.

**Interface texts** live in two places:

- `translations/source/ui_*.json` with `translations/<code>/ui_*.json`: the
  texts from the Qt era, keyed by their Qt context and the German text. The
  new interface still uses them. Each source entry has `id`, `context`, `de`
  (the source) and `en`. Entries with `"plural": true` need a list of forms.
- `app/src/i18n/new-texts.json`: texts that are new in the Tauri interface.
  Each entry has `context`, `de`, `en` and a `"tr"` object with one text per
  language code (`"tr": {"es": "...", "fr": "..."}`).

`app/scripts/gen-i18n.mjs` (run by `npm --prefix app run build`) builds the
interface catalogs in `app/src/i18n/generated/` from both places. With
`I18N_STRICT=1` (set in the CI) a missing interface translation fails the
build.

## File format

A translation of `source/core_x2.json` goes to `<code>/core_x2.json`, of
`source/ui_01.json` to `<code>/ui_01.json`, as one JSON object from id to
text. Translate from the English text; the German one helps where English is
ambiguous.

```json
{"c0": "...", "c1": "..."}
{"u3": ["form for one", "form for many"]}
```

## Rules

- Keep every placeholder exactly: `%1` to `%9` and `%n`. Their order may change.
- Keep line breaks (`\n`) and leading or trailing spaces as in the English text.
- Keep technical names as they are: OBD, OBD-II, EOBD, ELM327, STN, OBDLink,
  KKL, K-Line, CAN, UDS, KWP1281, KWP2000, DoIP, ENET, VIN, PID, ECU addresses,
  fault codes like P0171, protocol names, units (V, A, kW, kWh, km/h, °C, %),
  brand and model names, Caruspex.
- Use the words a mechanic in that country would use, plain and friendly, the
  way the German and English texts talk to a car owner.
- No long dashes (the characters U+2014 and U+2013); use a comma, a colon or a
  plain hyphen instead.
- Plural forms per language: 1 for zh, ja, ko, id; 2 for es, fr, pt, it, nl, tr,
  hi; 3 for pl, cs, ru, uk (one, few, many); 6 for ar (zero, one, two, few,
  many, other).

Before you hand in a language, run `py -I tools/i18n_rust.py --strict` for the
core texts and `I18N_STRICT=1 npm --prefix app run build` for the interface.
